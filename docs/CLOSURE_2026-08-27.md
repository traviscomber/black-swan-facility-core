## 1. Objetivo del cierre

Este documento fija el estado operativo y técnico de Blackswan Facility Core (BSFC) al cierre de la fase de construcción. A partir de este punto el sistema debe tratarse como una aplicación productiva: los cambios nuevos deben responder a evidencia de uso real, incidentes, requisitos regulatorios o decisiones explícitas de producto; no a expansión de alcance por defecto.

El cierre no significa que el software sea inmutable. Significa que existe una baseline identificable, una arquitectura entendible, controles de acceso definidos, runbooks de operación y una puerta de release verificable.

## 3. Qué queda cerrado funcionalmente

### Operating System

BSFC organiza la experiencia principal en seis áreas canónicas:

1. Hoy
2. Operaciones
3. Personas
4. Lugares y Activos
5. Finanzas
6. Red

La persona/rol puede cambiar el orden y la experiencia, pero no es una primitiva de autorización. Las capacidades, scopes y RLS continúan siendo la autoridad.

### Hospitalidad

`/bookings` es el cockpit principal de hospitalidad. La operación se apoya en reservas, habitaciones/camas, bloqueos, huéspedes, cargos, extras, pagos, facturas, housekeeping, handovers, actividades y logística.

Invariantes de cierre:

- no se admite doble reserva silenciosa;
- los intervalos de estadía son half-open;
- los room blocks participan en la validación;
- movimientos y cambios sensibles usan validación/flujo atómico cuando corresponde;
- los objetos Reservation y Room tienen rutas canónicas dedicadas;
- la política de origen de reservas falla de forma segura cuando el source no está autorizado.

### Trabajo operacional

Tasks, Maintenance, Issues, Checklists, Housekeeping y solicitudes de huéspedes forman la superficie operativa de trabajo. El OS prioriza trabajo asignado, aprobaciones y excepciones según el perfil efectivo del usuario.

### Inventario y activos

`/inventory` concentra activos, categorías, conteos, auditorías, intake, reposición, custodia/movimientos y vínculos con mantenimiento e incidencias. El objeto canónico Asset vive en `/inventory/[id]`.

### Procurement

El flujo canónico se entiende como:

`request → sourcing/quotes → comparison → approval → purchase order → receipt → receipt items → inventory intake`

La ruta canónica del objeto Purchase/Request es `/procurement/requests/[id]`.

### Finanzas

La superficie de Finanzas incluye Budget, approvals, documents, reconciliation, accounting e invoices de Hospitality. La navegación y las acciones dependen de capability/acción efectiva; los datos financieros no deben inferirse desde visibilidad de UI.

### Personas, Red y Discovery

Personas opera sobre empleados y contexto organizacional. Red agrupa Discovery, Events, Event Providers, Front Door y Education, incluyendo portales públicos controlados cuando corresponde.

### Administración e IT

Administración contiene access management, catálogos administrativos, auditoría y el IT Control Center. El panel IT lee estado vivo; no publica KPI de seguridad hardcodeados.

## 4. Objetos canónicos

Los objetos de referencia para navegación, soporte y auditoría son:

- Reservation → `/bookings/reservations/[id]`
- Room → `/bookings/rooms/[id]`
- Asset → `/inventory/[id]`
- Purchase/Procurement Request → `/procurement/requests/[id]`
- Work → Tasks / Maintenance / Issues / Housekeeping según dominio
- Invoice / Payment → superficies financieras y de Hospitalidad
- Person → Employees / perfil de acceso

El comando global `⌘K` es una capa de búsqueda read-only sobre objetos autorizados; no concede permisos y no usa service role en navegador.

## 7. QA y release gate

Un release no se considera cerrado por compilar. El gate de BSFC exige, según el alcance:

- typecheck;
- suites contractuales de inventario, mapa, booking, source policy, discovery, access y OS;
- browser E2E del calendario para cambios de Hospitality;
- verificación de deployment Vercel;
- smoke de dominio/rutas afectadas;
- revisión de runtime errors;
- verificación de datos/integridad cuando el cambio toca persistencia;
- rollback identificable.

Los escenarios críticos de Hospitality incluyen move, resize, swap, creation, undo, keyboard, pointer y touch/long-press, además de conflictos de inventario y room blocks.

## 8. Excepciones y riesgos conocidos

No son blockers de la baseline actual, pero siguen abiertos como hardening/evidencia:

1. **Supabase Auth Leaked Password Protection:** permanece desactivado. No debe marcarse como resuelto hasta cambiar y verificar la configuración de Auth.
2. **`btree_gist` en schema public:** advisory conocido; no mover en caliente sin análisis de dependencias.
3. **SECURITY DEFINER advisories:** existen funciones privilegiadas revisadas. No revocar en bloque; auditar función por función.
4. **Procurement end-to-end con uso real:** la arquitectura y contratos están implementados, pero la evidencia operacional de órdenes/recepciones/intake debe crecer con uso real; no sembrar datos ficticios para demostrarlo.
5. **Aceptación visual autenticada:** debe repetirse con usuarios reales/entorno visual disponible cuando se haga un cambio relevante de UI. No sustituirla por una afirmación documental.
6. **Preview `d239023…`:** parche editorial READY pero fuera de producción hasta promoción explícita.

## 9. Política posterior al cierre

A partir de esta baseline:

- no agregar features sin problema real o decisión explícita;
- no crear métricas sintéticas para llenar dashboards;
- no sembrar producción con datos demo;
- no debilitar RLS/auth para resolver fricción de UI;
- no cambiar schedules de cron sin registrar motivo, zona horaria, rollback y verificación;
- preferir cambios pequeños, reversibles y con evidencia;
- documentar todo cambio material que altere arquitectura, roles, rutas, jobs o contratos de datos.
